Part 03 · Hardware interface

From spikes to send_rc_control

The brain only outputs abstract intentions: escape, yaw, forward. This page covers how those become four integers sent over Wi-Fi to a real DJI Tello, and everything we built so that doing so is safe.

Akshin Makkar, Parth Joshi, Amal Chalayil Sreekumar interfaces/tello_drone.py · fly_tello.py

3.1The platform

The DJI (Ryze) Tello is a small consumer quadcopter with an onboard flight controller, downward vision positioning and a forward camera. It exposes a text-based SDK over UDP: commands go to the drone, and telemetry and H.264 video come back on separate ports. We drive it through djitellopy[1], a Python wrapper around that protocol that also decodes the video stream on a background thread.

The key design point is that the Tello stabilises itself. Unlike our simulator, which needs a PID cascade, we only request body-frame velocities and the drone's firmware handles attitude and motors.

3.2Connecting

The laptop joins the Tello's Wi-Fi access point, and every session then follows the same handshake:

tello_flight_test.py
from djitellopy import Tello
import time

tello = Tello()

tello.connect(wait_for_state=False)
print("Connected!")

battery = tello.query_battery()
print("Battery:", battery, "%")

tello.takeoff()
print("Flying!")

time.sleep(2)

tello.land()
print("Landed!")

3.3One interface, two drones

Everything above the hardware talks to an abstract DroneInterface with methods such as takeoff, land, hover, move_forward/backward/left/right, turn_left/right, get_camera_frame, get_state, step and reset. There are two implementations:

3.4RC control & unit conversion

send_rc_control(lr, fb, ud, yaw) takes four integers in \([-100, 100]\), each a percentage of the drone's maximum speed. Our controllers think in m/s and rad/s, so TelloDrone.step() converts:

$$\text{rc}_{v} = \operatorname{clip}\!\big(\operatorname{round}(60 \cdot v),\ -100,\ 100\big), \qquad \text{rc}_{\omega} = \operatorname{clip}\!\left(\operatorname{round}\!\left(\frac{\omega}{1.5}\cdot 100\right),\ -100,\ 100\right)$$(1)

The sign conventions also differ. In our codebase, positive yaw means turn left (counter-clockwise), and positive lateral velocity means move left. The Tello uses the opposite for both, so both are negated:

interfaces/tello_drone.py · TelloDrone.step()
def step(self):
    if self.state != "flying":
        return
    lr = _mps_to_rc(-self.target_vy)   # send_rc_control: +lr = right; move_right is -target_vy
    fb = _mps_to_rc(self.target_vx)
    ud = 0  # altitude changes not used by the hover/escape flight test; Tello holds altitude on its own
    # ... Tello's yaw_velocity is the opposite sign (+100 = cw/right), so flip it.
    yaw = _rate_to_rc(-self.target_yaw_rate)
    self._tello.send_rc_control(lr, fb, ud, yaw)

Known limitation · unverified scale factors. Both 60 %/(m/s) and 1.5 rad/s at 100% are assumptions, not measurements. Tello RC percentages are relative to the current set_speed setting, which we never changed. The code flags them to be verified with slow test moves before trusting them for a dodge.

3.5Video pipeline

streamon() starts a 960×720 H.264 stream, which djitellopy decodes on a background thread. Each control cycle:

  1. Reads the newest decoded frame and converts RGB → BGR for OpenCV.
  2. Resizes it to 320×240 (area interpolation). That is the resolution the optic-flow code was designed for, and it keeps Farnebäck flow within the frame budget.
  3. Detects djitellopy's black 400×300 placeholder frame (served before the decoder has real video) and returns the last good frame instead. Otherwise a black frame followed by real video would look like a massive looming event.

The optic-flow code needs the camera's field of view to undo rotation. The Tello's published 82.6° is a diagonal figure, so the escape flight test uses about 55.6° vertical.

3.6Position without GPS

The Tello has no GPS, and its velocity telemetry is often zero on non-EDU units. But the escape program needs to know how far into a dodge it has travelled. We dead-reckon by integrating the commanded body velocity, rotated into the world frame by the measured yaw \(\psi\):

$$\begin{bmatrix}x\\y\end{bmatrix} \mathrel{+}= \begin{bmatrix}\cos\psi & -\sin\psi\\ \sin\psi & \cos\psi\end{bmatrix}\begin{bmatrix}v_x\\ v_y\end{bmatrix}\Delta t$$(2)

This works because the Tello tracks commanded velocity fairly directly and does not coast much once told to stop. It is good enough to time a roughly 1 s dodge, but it is never used for absolute navigation. Boundary containment is disabled on hardware.

3.7Safety systems

A bug in a simulator costs a restart. A bug on a real drone costs a propeller, or worse. Several independent layers guard every flight:

LayerBehaviour
Dry run by defaultfly_tello.py streams and runs perception but never takes off unless given --fly.
Battery gateRefuses to take off below 30%. battery.py reports "OK to fly" and has a --watch mode.
Hard timeoutThe escape flight test auto-lands 60 s after takeoff (--seconds).
Operator keysq land · e gentle stop-and-land · x emergency motor stop (banana flight). l land · q/space hover then land (escape test).
Clean shutdownZero RC command, wait 1 s, then land().
Rate limitsAll RC values clipped to ±100. Feeding behaviour caps lateral and vertical at 20%.

3.8Feeding behaviour on the Tello

The banana "hunger" behaviour (NeuralPathways/FoodNeuron/feeding_behaviour.py) runs the banana network on every frame and drives a small state machine:

Hunger starts at 100 and falls at 15 units per second while a banana is in view, so "eating" to the full threshold of 10 takes about 6 s:

$$t_{feed} = \frac{100 - 10}{15\ \text{s}^{-1}} = 6\ \text{s}$$(3)

During FEED the drone never flies toward the banana. It makes deadzoned, smoothed corrections to keep the banana centred, and backs off at 10% if the banana grows past 25% of the frame.
